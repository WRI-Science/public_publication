Structure Loss Pipeline · the dataset

The Dataset

This project estimates, building by building, which structures a wildfire destroyed, using free satellite imagery and public maps of building outlines. It produces a per-building record for each fire, not a single loss total. This page describes the file that record ships in: what one row is, what the columns mean, how much of it there is, where each part came from, the licence, and — most important — the rules for counting it without getting a wrong answer.

What you get

One file, 377 fires, 2,069,752 rows. One row is one building, in one fire, as described by one source. 361 of those fires come from the published historical record — a hand-assembled record of buildings destroyed in United States wildfires between 2002 and 2022, one point per destroyed building, compiled by Carlson and colleagues and carried here unchanged: 1,770,939 rows. 16 are fires of 2024–2025 that this project's model produced. A further 17 are fires the historical record already covers that this project has also enumerated independently, so they appear twice, once from each source.

The full internal build is 2,102,662 rows. 32,910 of them (1.57 %) are left out of the released package for the licence reason set out at the bottom of this page.

⚠️ Never add up rows across sources for the same fire. Every row carries a column called series_source, whose value is either carlson (the published historical record) or slp (this project's model). Seventeen fires appear under both values, and neither description is a subset of the other: one is the historical record's hand enumeration of that fire's buildings, the other is this project's independent inventory of the same buildings.

Always group by (fire_id, series_source), and pick one source before you pool. Here is what happens if you do not: take one of those seventeen fires, total its destroyed buildings without splitting on series_source, and you have counted that fire's losses twice over — once as hand-recorded points and once as model calls on the same buildings — so the fire's loss total comes back at roughly double what happened, and a national total built the same way is inflated by the whole of those seventeen second descriptions.

The layer is built so this cannot happen by accident. The building identifier is namespaced per source, so no two rows can collapse into one; the fire identifier is deliberately the same on both sides, so the two descriptions are visibly of one fire. The layer holds 394 (fire, source) pairs over 377 fires, and the released summary tools refuse to aggregate across them.

Source: the release directory's manifest.json on the data share, and the crosswalk document docs/combined-series-spec.md shipped inside every release.

Reading it: each line is one period of time as described by one source, so the two lines in the middle block are the same seventeen fires seen twice and must not be added together; only the "Fires" column in the total row, 377, counts each fire once.

Two other terms in that table. The primary call is this project's estimate made about two and a half months after a fire starts, from before-and-after satellite images: the model gives each building a probability of having been destroyed, and we call it destroyed when that probability is above a fixed threshold of 0.85, chosen in advance and never tuned fire by fire. The advisory call is an alternative offered in the same file for users who want it, made at a threshold chosen separately for each fire rather than fixed; it is never mixed into a headline number. The rows with no call have neither, with a stated reason.

The file is combined_structures.gpkg: 68 columns in EPSG:5070, a standard equal-area map projection for the continental United States. Every row carries series_source, an era whose boundaries are satellite launch dates rather than preferences, harmonised damage fields, provenance for that individual row, and whatever uncertainty its source can support: this project's rows carry destroyed_prob, the model's probability; the historical record's rows are explicitly null there rather than given an invented number. A field only one source can fill is null on the other side and is never back-filled.

On this project's side, every fire is treated identically: one building detector, one study-area definition and one damage model throughout. Accuracy here is always measured out of sample — the model that scores a fire is trained only on other fires, so it has never seen the fire it is scoring. A provenance column records on every row whether the call came from the production model, which had never seen that fire, or from a model refitted with that fire held out because the fire otherwise sits in the production model's training pool. A score from a model that saw the fire is never shipped.

Every one of the historical record's 1,770,939 rows also carries ten geometry columns — which source produced the building's analysis polygon, how confident that is, what kind of image cell it owns, how many cells it owns, and whether this project's building detector found it. Those columns join onto 100.0000 % of rows on all 361 fires, with a maximum coordinate displacement of 1.3 × 10⁻⁸ m. How they were made is on the historical companion.

Source: the release directory's manifest.json and augmented_geometry_coverage.csv on the data share (361 rows, minimum fraction_joined 1.0, tolerance 0.5 m).

03 · against the official counts

How the modern counts compare with inspectors' and incident reports

Two reference counts appear here. CAL FIRE DINS is California's Damage Inspection programme: after a fire, inspectors visit each structure inside the burn area and record whether it was destroyed, damaged or untouched; it is the ground truth this project is measured against. ICS-209 is the incident situation report an incident commander files while a fire is burning, which carries a running destroyed-structure count.

Source: the two prediction columns from outputs/combined_series/per_fire_summary.csv on the data share, the truth column from outputs/forward_damage/per_fire.csv (n_dins_destroyed).

⚠️ Compare like with like: use the major-buildings row, not the all-categories one. The historical record counted major buildings only. Inspectors also visit sheds, detached garages and mobile homes, and several inspection records can sit on one building. Measured in the historical record's units the ratio is 1.135, not 0.828. Note too that in California the incident-report count is not independent of the inspections: 12 of the 14 matched fires give a ratio of exactly 1.000, because the same agency runs the damage inspection and files the situation report. That agreement confirms the two records are wired together correctly; it is not independent corroboration.

04 · across the join

Can you plot a trend that crosses the two halves?

Only with care, and only for some kinds of trend. The answer comes from the seventeen fires described by both sources, where the two can be compared directly.

Reading it: the damage call itself agrees with the historical record almost perfectly, so nearly all of the gap between the two halves comes from which buildings each one lists, not from which buildings each one calls destroyed.

The terms in that table: agreement is the share of buildings where the two give the same answer; κ is that agreement corrected for the amount you would expect by chance, on a scale where 1 is perfect; F1 combines precision (what share of destroyed calls were right) with recall (what share of the real destruction was found) as their harmonic mean, so it punishes both errors; AUC is the probability that a destroyed building scores higher than a surviving one. The full counts behind these are on the confusion matrix page.

⚠️ Three things follow for anyone plotting across the join.

1. Apply a factor of about 0.77 to a modern destroyed count before comparing it to a historical one — and do not treat that factor as stable. It runs from 0.48 to 1.80 across the seventeen fires, and it tracks how completely the buildings were found, not anything about the damage model.

2. That factor is the net of a large miss and a large addition. On those fires the model recovers 6,451 of the historical record's 10,808 destroyed buildings in the shared region, and adds 1,862 destroyed calls on structures the record did not list as destroyed, 970 of them on buildings it never enumerated at all. The two partly cancel.

3. The threat to a trend is which fires it contains, not which years. The gap does not drift with the year; it drifts with the fire, and it tracks how much of a fire's building stock burned. A trend built from catastrophic fires crosses the join safely; one that mixes in many low-loss fires does not.

Source: outputs/combined_retrospective/end_to_end.csv and damage_trend.json on the data share.

Two flags to apply before counting the historical half

The historical record is carried verbatim. Nothing is dropped, merged, re-attributed or corrected: it is the published release as its authors issued it, and quietly cleaning another team's published census inside a derived product would make the two impossible to reconcile. A user who counts rows in the carlson half gets exactly what they would get counting rows in the source shapefile. Two properties of that release will nevertheless break a naive count, so they are measured once over the whole national file and shipped as columns:

Source: outputs/combined_series/manifest.json on the data share, measured over the whole national release before any subset is applied, and the crosswalk document docs/combined-series-spec.md. Both columns are null on every slp row. The duplicate flag marks 20,296 rows in 40,580-row duplicate groups at 20,284 distinct duplicated rows; the multi-fire flag marks 324,910 rows at 152,537 of the release's 1,589,122 distinct locations.

Reading it: about one row in five on the historical side sits at a location some other fire also claims, so a national pooled count that ignores these two columns will be too high.

One fire carries most of the duplication: the 2008 Sayre fire in California, CA_2008_SAYRE in the record's own identifier, holds 19,859 of the 20,296 repeats — 40,146 rows at 20,287 locations. A national destroyed count that does not drop them is wrong by that much. The multi-fire flag marks every row at such a location, because without an attribution rule there is no later fire to prefer. De-duplicate on geometry before any pooled count across fires in the historical half. These are flags, not fixes: multi-fire locations are a correct consequence of a definition — one row per building per fire — that this file shares.

The same exposure is measurable on both halves of the shipped layer. 328,786 of the historical record's 1,770,939 rows (18.6 %) and 9,264 of this project's 168,197 (5.5 %) sit where another fire also enumerated a building, and 34 locations are coded destroyed under more than one fire — all of them on the historical side, because on this project's side the rule that assigns an overlapping building to a single fire takes that number to zero.

Source: outputs/forward_damage/overlap_series.json on the data share.

The code is MIT-licensed, the data is CC BY 4.0, copyright Carlo Broderick. Cite the dataset and this copyright line when you use it. One of the public building-outline databases behind the inventory is published under the Open Database Licence, which would impose share-alike terms on anything redistributing it, so the question is settled by exclusion rather than by argument: every row whose building outline came from that database is dropped from the package — 32,910 of 2,102,662 rows (1.57 %) across 29 (fire, source) pairs, every one of them on this project's side. None of the historical record's 1,770,939 rows is touched.

⚠️ The exclusion is uneven, and it is largest exactly where the other building databases are weakest. It removes 0.03 % of the rows for Atlas 2017 and 36.1 % of those for CZU 2020, with South Fork NM at 28.4 % and Dixie 2021 at 16.5 %. If you count buildings from the package on a rural fire, you are counting a filtered inventory. The internal build keeps those rows, and every accuracy number this project publishes is computed on the unfiltered version.

That database was also used as a training aid for this project's building detector, which is a different act from redistribution: the network reads an extra image band saying a building database has an outline here, and the resulting weights and every building the detector outputs are this project's own work. No polygon, attribute or identifier from that database is redistributed in any form.
